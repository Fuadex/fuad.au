# Rotation — November 2026 audit (gigs program)

Scoped audit run 2026-11-05, same day the gigs program landed (country-wide Japan concert
database, weekly no-LLM sweep, issue-based marks, gigs.ics feed, discovery shelf, market-chip
filters). Four lanes: static invariants (the repo's own audit tooling) · code review of the
program diff (`c2536bf..HEAD`, 8-angle pass) · a Playwright runtime walk of the staged site ·
a data-quality pass over `data/concerts-tokyo.json`. Every finding below was fixed the same
day unless marked open.

## Verdict, up front

The program shipped healthy: all 22 JSX files evaluate, smoke/global/hook audits pass, the
staged site boots **with zero console errors on every page** (hub, rotation incl. the new Gigs
interactions, culture, canvas, mobile), and the 802-row concert database has no bad dates, no
out-of-Japan coordinates, no duplicate (artist, date) pairs. The real findings were all in the
day-old automation plumbing — two silent-failure paths, one injection surface, one deploy-lag
surprise — exactly the class of thing an audit on landing day is for.

## Findings → fixes (all same-day)

| # | Finding | Fix |
|---|---|---|
| 1 | `gig-marks.yml` shell-interpolated the issue title and script output via `${{ }}` inside `run:` (owner-gated, but an injection surface — artist names with shell metachars reach it through ordinary data) | all untrusted text now enters the shell via `env:` only |
| 2 | Both workflows swallowed push failures (`git push \|\| echo "nothing to commit"`): a race with a concurrent commit silently lost the mark / the week's sweep while reporting success | commit and push separated; `git pull --rebase` before push; failures now fail the run (and comment on the mark issue); both workflows share a `concurrency` group |
| 3 | `GITHUB_TOKEN` pushes don't fire `sync.yml`'s push trigger, so marks/sweeps deployed only at the next daily cron (≤24 h) while the issue-close comment claimed "already triggered" | both workflows get `actions: write` and dispatch `sync.yml` after a successful push; the comment now tells the truth |
| 4 | Weekly sweep committed three overlapping MB-scale archives per run (`listings-sweep-*` plus merge's `listings-research-*`/`matches-research-*` copies) — hundreds of MB/year of redundant JSON | `merge_listings.py --no-archive` (used by the sweep); workflow commits only the sweep file + concerts + discoveries, and prunes sweep files older than 90 days **by filename date** (CI checkouts reset mtimes, so `find -mtime` can never fire there) |
| 5 | The wrong-entity REJECT list (bed→Bed, vkei Razor→Razor) lived in `merge_listings.py` only — `concert_agent.py`'s own merge path was unprotected | moved into `rotation_match.py` (acts are dropped at match time), covering every consumer |
| 6 | UI offered want/undo but no skip — new rows couldn't be dismissed from the site | skip button added (skip-marked rows leave the map/list at the next deploy) |
| 7 | `gigs.ics` didn't fold lines at 75 octets (RFC 5545 §3.1) — long Japanese summaries exceeded it | byte-aware folding added in build-data's emitter |
| 8 | Three scripts hand-rolled `--flag` parsing; the same value-swallowing bug shipped twice in one day (apply_mark, discover) | all on argparse now |
| 9 | Sweep fetch loop had no politeness delay (~500 sequential requests against small venue sites from a fast CI runner) | 0.4 s pause per request (~3 min added, within the 35-min budget) |
| 10 | Mobile `want` tap target was 38×15 px | `pointer: coarse` padding bump |

## Local-dev note

A fresh clone can't stage: `rotation/live-data.js` needs `LASTFM_API_KEY` (CI secret) and
`rotation/about/` needs `node shard-about.js`. For a local walk, stub
`window.ROTATION_LIVE = null` into live-data.js and run shard-about; CI generates both for
real. `gigs.ics` is likewise emitted by `node build-data.js` (gitignored, in the deploy list).
